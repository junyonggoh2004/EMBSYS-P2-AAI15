# D5 Benchmarking Programme on ESP32-S3 µT-Kernel 3 SMP

This checklist is based on `s3-port-d1-redesign` at `8fb9ec1` and the professor's **Change Requirement 3**, supplied separately. The required firmware is the course µT-Kernel 3 SMP port in [`esp32s3_mtk/`](esp32s3_mtk/). All application tasks, scheduling, inter-task communication and synchronisation must operate through µT-Kernel. D5 must measure whether the redesigned configurable edge platform remains correct and performant on real hardware, including the cost and benefit of configurability. **This file is a plan. It contains no final D5 benchmark results.**

The Arduino/FreeRTOS firmware in `esp32s3_edge/` is retained as a historical same-board runtime comparison. A separate fixed-configuration build on **the same µT-Kernel runtime** is needed to isolate the cost of configurability. A Pico-to-S3 comparison may provide context but cannot isolate either effect. Existing D1 logs are pilot/reference evidence; final D5 values need the approved D5 protocol and repeated hardware runs.

## Scope and dependencies

It does not move application work back to FreeRTOS or Arduino.
- [`parity/timing_test.py`](parity/timing_test.py), [`parity/wcet_test.py`](parity/wcet_test.py), [`parity/endurance_test.py`](parity/endurance_test.py), `tools/mtk.sh`, and `parity/logs/mtk/` provide test fixtures and pilot data. The `TASKS` cycle maximum is the **largest observed cycle**, not a proven worst-case execution-time bound.
- D1 task 32 still lists jumper/light-sensor rows as hardware pending, and its model suite records 8/9 because the test reopens the port after the model has already loaded. Resolve or explicitly scope these evidence gaps before claiming all required functionality in a D5 integrated result.
- The [Week 6 feedback tracker](WEEK6_FEEDBACK_RESPONSE.md) names D5's B1–B6 programme and specifically calls for sampling jitter tails (F16), SchedulerTask cycle measurement (F6), and the 50 ms mixed-sensor risk (R1). The repository describes a B2 SPI method in [`D2_D4_RESEARCH_CONTEXT.md`](D2_D4_RESEARCH_CONTEXT.md#46-b2-benchmark-method) and a B5 ML method in [the same file](D2_D4_RESEARCH_CONTEXT.md#57-b5-benchmark-method). The definitions of the remaining B1–B6 items must be reconciled with the team's submitted review before assigning those IDs to new results.
- D2's current SPI performance data were captured on its Arduino path. SPI benchmarking on the required µT-Kernel firmware waits for the D2 owners to port and validate that driver; do not present the Arduino data as µT-Kernel data. The full 50 ms entrance workload also depends on D3's timing decisions, D4's selected model, and D6's frozen event and sensor workload. Record these as dependencies rather than inventing a result.

| ID | What to measure | Why it matters | Required comparison or condition |
|---|---|---|---|

| D5-M04 | Input-to-rule-output latency, GPIO pulse/ISR timing, I2C/UART service rate and integrity; SPI only when the D2 µT-Kernel path is ready | Shows whether real sensor and actuator paths remain responsive under the new kernel and SMP assignment | Repeatable physical stimulus and capture, alone and with concurrent tasks |
| D5-M05 | MQTT delivery latency, throughput, drops, reconnect time and message-buffer occupancy under controlled load | Tests remote configuration and telemetry while Wi-Fi, MQTT and sampling run on their assigned cores | Same broker, network and workload; idle and loaded µT-Kernel; record radio stalls separately |
| D5-M06 | Inference latency, throughput, output agreement, model-switch interruption, arena/heap use and effect on sampling | Tests ML cost in isolation and in the configurable edge workload | Same approved model, input and build settings; µT-Kernel alone and with sensors/MQTT |

Power/energy per event is optional until a calibrated meter, wiring, sampling interval and baseline are available. Never infer energy from timing or report an unmeasured value.

## Fixed measurement method to approve before final runs

1. **Freeze the system.** Record board/module and flash/PSRAM identity, power source, wiring and stimulus, sensor/model hashes, firmware commit and binary hash, course-port commit, ESP-IDF/compiler/component versions, build options, task-to-core table, broker/network configuration and host clock. Use [`SETUP.md`](SETUP.md#esp32-s3-on-µt-kernel-3-smp-tasks-2534) and `sh tools/mtk.sh check` to record the actual environment.
2. **Freeze each workload.** Version the exact configuration lines, stimulus pattern, input rate, model, MQTT payload/rate, warm-up and run duration. Specify which real sensor or electrical fixture is connected. Reset or clear state in a fixed order. Alternate paired-build run order. When switching from µT-Kernel to the Arduino baseline, follow SETUP.md's flash-erase procedure because their model and LittleFS partitions overlap; re-provision the model before comparing. Keep D2, D3, D4 and D6 features out of a final integrated claim until their interface and workload are frozen.
3. **Measure the intended interval.** Use on-board monotonic timestamps for scheduler, configuration, inference and message-buffer operations. Use one external clock or instrument for physical input-to-output latency. Timestamp MQTT at both defined endpoints and distinguish application enqueue, wire delivery and broker receipt. Do not use the host's delayed Serial Monitor display as a real-time clock. Time the measurement code itself, including the `bench_mbf` path; set and record its capacity, timeout and drop policy. Do not print per event inside a timed section.
4. **Repeat complete runs.** Proposed starting rule for team sign-off: at least five independent runs per condition after warm-up; at least 100 events per run for interval/latency metrics; at least 20 independent configuration changes; at least three 30-minute sustained runs. Report run count, event count, mean, median, standard deviation, p95, maximum and error/drop count. If the cumulative mean changes by more than 5% on adding the final run, investigate and extend the series; retain and explain outliers and failed runs. A measured maximum is not a proven WCET bound.
5. **Fix acceptance limits before collecting final data.** Carry D1 NFRs forward as references, then agree D5 limits for deadline misses, tails, throughput, memory and reconfiguration benefit. Do not quietly turn a pilot observation into a target. Flag any conflict with D1, D3, D4 or D6 requirements for team review.
6. **Keep raw evidence.** Save each run's timestamped observations, setup manifest, test script version, outcome and notes, including invalid and aborted runs. Generate summary tables and plots from raw files. Do not copy one-off D1, D2 or Arduino results into D5's final-result columns.

Create the execution artefacts under `benchmarks/` when measurement work begins: `README.md` for the approved protocol, `fixtures/` for workloads and the fixed µT-Kernel baseline, `scripts/` for capture/analysis, `raw/` for per-run data and metadata, and `results.md` for calculated comparisons and limitations. The planning checklist lives here so the existing D1, D2 and Pico files remain intact.
