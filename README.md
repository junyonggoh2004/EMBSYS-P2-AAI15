# D1 — ESP32-S3 Port and Design-Review Checklist

Branch: `s3-port`. The Pico 2 W build is the verified reference against which ESP32-S3 behaviour, timing, and limitations are measured.

Pico reference build and ESP32-S3 Arduino setup instructions are in [SETUP.md](SETUP.md). The framework configuration syntax and command reference are in [project_v3/README.md](project_v3/README.md).

**Requirements and parity table: [parity/PARITY.md](parity/PARITY.md).** This is the single reference for what the port must do and how each part is proven. Every task from 11 onward must name the requirement IDs it satisfies (`FR-`, `NFR-`, `T-`), fill in the ESP32-S3 column of its rows using the same commands as the Pico (`python3 parity/parity_test.py --stage <stage>`), and record any new behaviour, defect or measurement in that file rather than anywhere else.

The ESP32-S3 port uses Arduino IDE and the Arduino-ESP32 core. Arduino CLI may be added as the repeatable command-line build interface, but it does not replace verification through the team's agreed Arduino IDE workflow. Shared configuration, scheduling, sensor, rule, output, MQTT, and inference logic must call portable interfaces instead of Pico SDK or Arduino APIs directly. Direct underlying ESP-IDF APIs may be used from Arduino only when the Arduino API is insufficient; each exception must stay below the shared-code boundary and be documented and tested. The exact Arduino IDE, Arduino-ESP32 core, board profile, USB settings, flash/PSRAM settings, and later library versions remain unconfirmed until tasks 7–8 record them in `SETUP.md`.

## Execution model

- Tasks 1–3 establish the common baseline. Their implementation work is complete; any missing build log or artifact metadata must be backfilled before task 10.
- After task 3, tasks 4–6 (Pico requirements and reference evidence) and tasks 7–9 (ESP32-S3 environment and board bring-up) run concurrently.
- Task 10 is the architecture-freeze gate. It cannot be completed until both parallel tracks are finished.
- Tasks 11–13 establish the portable HAL, shared build, and FreeRTOS runtime.
- After task 13, the GPIO path (tasks 14–15), I2C (task 16), and UART (task 17) may be developed in parallel where file ownership does not overlap.
- Tasks 18–20 integrate application services. Final model-transfer verification in task 20 depends on MQTT from task 19.
- Tasks 21–23 are the verification, documentation, and release gates.

Every completed task must identify the tested commit, hardware revision, tool versions, tester, date, and retained evidence. Evidence may include console logs, broker captures, measurements, photographs, or test scripts.

## Completion rule

A task is not complete merely because code compiles or a single happy-path demonstration works. It is complete only when its acceptance evidence is recorded, relevant requirements and assumptions are updated, and any failure or limitation is either fixed or explicitly documented with an owner and disposition.
